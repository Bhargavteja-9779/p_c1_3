## Findings

### R5-01 — MAJOR — `run_all.py --mode full` from a clone recomputes nothing
Location: `code/experiments/suite.py:24-37` (`_exists`, `_chunk`); `code/README.md` §3; Data Availability Statement (`manuscript/src/part3_discussion_backmatter.md`, rendered `Draft_Manuscript.md:270`).
Evidence: the committed `results/raw/*.csv` and `results/raw/chunks/*.csv` trigger the resume logic. In the clone:
```
python run_all.py --mode full --stages experiments
... E1 matr_clo: outputs exist, skipped (resume)
... E2_models_splits.csv: exists, skipped (resume)  ... (every experiment skipped in 0 s)
```
The Data Availability Statement says the code "regenerates them (`python run_all.py --mode full`)" and the README gives the same command; a reader who follows it will "reproduce" the paper by re-reading the authors' files. `--force` exists but is mentioned only in a docstring.
Fix: in README §3 and the Data Availability Statement give `python run_all.py --mode full --force` (or make full mode write to a fresh directory / refuse to reuse outputs whose recorded code hash differs). State explicitly that committed results are re-used unless `--force` is given.

### R5-02 — MAJOR — No licence file; Data Availability has no archive/DOI
Location: repository root / `code/`; `code/README.md` §7 ("Code: MIT"); `Draft_Manuscript.md:270` ("[repository URL / archival DOI to be inserted at submission]").
Evidence: `git ls-files | grep -i licen` → nothing. Without a LICENSE file the code is legally all-rights-reserved regardless of the README sentence. The repository also redistributes derived data (feature tables, per-cell results) from MATR/CLO and HUST (both CC BY 4.0 at source) without a data licence/attribution notice.
Fix: add `LICENSE` (MIT text, copyright holder, year) and a `DATA_LICENSE`/NOTICE for `data/features` and `results` (CC BY 4.0, with attribution to Severson 2019, Attia 2020, Ma 2022); add `CITATION.cff`; archive a tagged release on Zenodo and put the DOI in the Data Availability Statement before submission.

### R5-03 — MAJOR — Environment is not pinned and the recipe does not match the environment used
Location: `code/requirements.txt`, `code/environment.yml`; Methods (`Draft_Manuscript.md:113`: "Python 3.13.18, scikit-learn 1.9.1 and PyTorch 2.15.0").
Evidence: requirements use only lower bounds (`numpy>=2.0`, `pandas>=2.2`, `scikit-learn>=1.5`, `torch>=2.2`). `environment.yml` pins `python=3.12`, whereas all results were produced with Python 3.13.18, numpy 2.5.3, scipy 1.18.1, pandas 3.0.5, scikit-learn 1.9.1, torch 2.15.0 (`results/run_config.json`, experiment logs). README says "Python >= 3.10". The bit-exact reproduction above was obtained only because the container has exactly those versions; ElasticNetCV/LogisticRegressionCV/GBR/RF/GP and the CNN are not guaranteed to give identical results across sklearn/torch versions, and pandas 3 vs 2.2 behaviour (copy-on-write, string dtype) was never tested (UNVERIFIED that pandas 2.2 works at all).
Fix: add `requirements-lock.txt` (exact `pip freeze` of the run environment) and set `environment.yml` to `python=3.13` with exact pins; keep the loose file as "compatible" with a note that exact reproduction needs the lock file. Report numpy/scipy/pandas versions in SI S1 too.

### R5-08 — MINOR — Absolute paths committed
Location: `manuscript/Draft_Manuscript.md` (9 image links), `manuscript/Supporting_Information.md` (4), `results/run_config.json` (raw/processed), `code/config/default.yaml:3-4` (default `/home/user/data_raw`), `PROJECT_STATE.md`.
Evidence: `grep -c /home/user` → 9, 4, 2. Re-rendering in the clone changes these to `/tmp/claude-0/r5_repro/...`, i.e. the committed `.md` files are machine-specific and not byte-reproducible. A third party running without `BATSCREEN_RAW` set gets a write attempt to `/home/user/data_raw`.
Fix: in `render.py` emit image paths relative to `ROOT` (pandoc already gets `--resource-path ROOT`); default raw path `../data_raw` (relative, gitignored); strip machine paths from `run_config.json` or record them as relative.

### R5-09 — MINOR — `render.py` does not document its system dependencies; Math check is Linux-only
Location: `manuscript/build/render.py:1-20, 269-274, 463-471`; `manuscript/build/check_docx.py:83`; README has no section on building the manuscript.
Evidence: the docstring lists tokens and options but not that it shells out to `pandoc` (tested here with 3.1.3; OMML output and table handling are version-sensitive), `soffice` (LibreOffice) for `--pdf`, the `libreoffice-math` component (otherwise equations are silently dropped — the project already hit this bug, `PROJECT_STATE.md`), `python-docx`, and `pdfinfo` (poppler-utils) for `check_docx.py`. `_check_soffice_math()` globs only `/usr/lib*/libreoffice/program/libsm*.so`, so it raises "LibreOffice Math is not installed" on macOS/Windows or `/opt/libreoffice*` installs even when Math is present. No `shutil.which` check, so a missing pandoc gives a bare `FileNotFoundError`.
Fix: add a "System requirements" block to the docstring and README (`apt-get install pandoc libreoffice-writer libreoffice-math poppler-utils`; pandoc ≥ 3.1 tested 3.1.3; LibreOffice version used), check `shutil.which("pandoc"/"soffice")` with clear errors, and detect Math by test-converting a one-equation docx (or broaden paths) instead of hard-coded Linux paths.

### R5-11 — MINOR — No integrity check linking committed feature tables to raw data
Location: `code/src/batscreen/data/download.py` (size check only), `data/features/*.npz`.
Evidence: downloads are verified by byte size, not hash; no checksum file for the four `.npz` feature tables; therefore a reader who rebuilds features from raw data cannot tell whether they match the committed tables (UNVERIFIED here: raw data absent). Server-side file replacement with equal size would go undetected.
Fix: add SHA-256 for the five raw files to `download.py` and a `data/features/SHA256SUMS`; have `build_features.py` print/compare hashes.

### R5-12 — MINOR — Possible look-ahead in HUST features; leakage test does not cover HUST
Location: `code/src/batscreen/preprocessing/features.py:89-97` (`hust_features`), `:28-33` (`_nearest_valid`); `code/tests/test_features.py`; SI S3 ("All features at checkpoint k use cycles ≤ k only; this is enforced by a unit test").
Evidence: if the V(Q) curves at cycle k and the previous stored cycle are both non-finite, `_nearest_valid(cell["vq"], cyc.index(k), 1)` tries index +1, i.e. cycle k+10 (stored cycles are 1..20, 20..1000 step 10). The tests exercise only `matr_features` and `capacity_features`; `hust_features` (and `difference_curve`) are untested. How often the fallback fires is UNVERIFIED (needs raw data). Also `vq_cycles` contains 20 twice (`preprocess.py`: `range(1,21) + range(20,1001,10)`).
Fix: restrict the fallback to non-positive shifts; add a HUST look-ahead test; deduplicate cycle 20; report (in `build_features.py` output) how many HUST cells hit the fallback.
